`stealth` / `script` / `align` / `library` / `doc` 五个模块，以及 `win` 里的
`geometry`、`click_through` 两个子模块，**完全不认识 Tauri** —— 只有纯数据和纯函数，
可以单独拿出来跑单元测试：

```bat
cd src-tauri
cargo test
```

这条界线不是洁癖，它直接决定了两件最容易写错的事能不能被钉住：
**「副屏拔掉后窗口会不会跑到看不见的地方」**和**「光标在控制区边缘时穿透会不会来回抖」** ——
两件事都依赖真实屏幕/真实光标，靠手工点是测不出边界的，抽成纯函数后各写十来个用例就行。

`doc` 同理但更彻底：它的核心是「吃一段 XML 字符串、吐纯文本」的纯函数，
所以"段落怎么分、实体怎么解、备注页的页码字段怎么排掉"全都能脱开真实的 Office 文件被验证。
只有最外面那层"从 ZIP 里取哪个条目"碰字节 —— 而那一层窄到一眼能看完。

`win/mod.rs` 里只剩「读一次光标位置 → 调一次窗口 API」这层薄壳，
`tray.rs` 里只剩「拼菜单 → 在主线程上执行」，它们不做判断，只执行判断结果。

## 几个关键技术决策

### 隐身：三个平台三套策略，而且「隐身」是增强项不是依赖项

| 平台 | 机制 | 可靠性 |
|---|---|---|
| Windows 10 2004+ | `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` | 公开 API，稳定 |
| macOS ≤ 14 | `NSWindow.sharingType = .none` | 公开 API，稳定 |
| macOS ≥ 15 | 私有 API `CGSSetWindowCaptureExcludeShape` | **可能随系统升级失效** |
| Linux | 无通用方案 | — |

因此产品设计上做了两条退路，任何平台失效都不至于开不了会：

1. **只共享指定窗口** —— 共享时选 PPT 窗口而不是整个屏幕
2. **第二设备** —— 稿件跑在手机/iPad 上（尚未实现，但这是唯一不依赖系统 API 的方案）

另外这一层有个容易被忽略的细节：**每次切换后都会回读确认**。
`SetWindowDisplayAffinity` 在部分环境下会「返回成功但实际没生效」，
不回读就等于把这个风险留给用户在真会议上发现。

### 语音对位：为什么不是「逐词编辑距离」

语音识别有两个和文本 diff 完全不同的特性：

1. **会回头改**。同一句话一秒内可能输出 `第三季度营收` → `第三季度营收增长` → `第三季营收增长`。
   纯编辑距离会把这些修正当成真实位置变化，光标来回抖。
2. **长度不对等**。识别结果里的数字、标点、口语填充词都不在稿子里。

所以这里的做法是：

- 只拿识别结果**末尾 16 个字**去匹配（末尾才是"刚说到的"，前面上一轮已经用过了）
- 在稿件的一个**受限窗口**内滑动搜索（默认往前走 240 字、往后回 40 字），
  天然抑制"跳到后面某个相似段落"这类误判
- 用 **LCS 比率**打分而不是编辑距离 —— LCS 对"多出来的字"和"少掉的字"同样宽容
- 加**单调性约束**，位置不能倒退超过窗口下界
- 连续 6 次匹配失败就**放开窗口做全稿搜索**，处理"用户中途跳了一段"的情况

### 数字处理：丢掉阿拉伯数字，但**保留汉字数字**

这一条是被单元测试逼出来的修正，值得单独写下来。

稿件写 `2026年第三季度营收50%`，你嘴上说的是「二零二六年第三季度营收百分之五十」。
阿拉伯数字和读法之间没有确定映射（「2026」可以读成「两千零二十六」，也可以读成「二零二六」），
猜错反而引入新错位。所以**阿拉伯数字、全角数字、小数点、百分号一律丢弃**：

```
稿件侧：2026年第三季度营收50%        →  年第三季度营收
语音侧：二零二六年第三季度营收百分之五十  →  年第三季度营收
```

但**汉字数字必须留下**。最初的实现是「所有数字类字符通通丢弃」，
于是 `第一季度` / `第二季度` / `第三季度` 归一化后全都变成 `季度` ——
光标停在哪一段都算匹配，汇报里**最不能错的序号反而第一个失准**。
汉字数字本身就是朗读内容，不存在歧义，没有任何理由丢掉它。

代价是纯数字行（孤零零一个 `2026`）无法参与定位，但它们本来也不是朗读内容。

### 鼠标穿透：判据必须是纯函数，而且必须**有迟滞**

「鼠标移到稿件区就穿透，让点击落到下面的 PPT 上」听起来是个一行的功能 ——
实际上 `set_ignore_cursor_events` 是**整窗口粒度**的，没有"部分穿透"；一旦穿透，
前端连 `mousemove` 都收不到（事件已经被穿到下层窗口去了）。
所以「光标现在在不在控制区里」**只能在后端判断**。

这带来一个真实的风险：如果在 40ms 的轮询间隙里，用户从稿件区快速划向控制栏并按下去，
那一下点击就会穿到 PPT 上 —— 在正式汇报里可能点掉放映。朴素实现必定踩这个坑。

所以这里用了**迟滞**（`win/click_through.rs`）：

- 进入**外扩 24px** 的控制区 ⇒ **立刻**变可点（宁可提前，也不能漏点击）
- 离开外扩区 ⇒ 还要**连续 3 个 tick（约 120ms）**都在外面，才切成穿透
- 调用方只在判定返回 `Some(..)` 时才去碰窗口 API ——
  这条约束是**类型层面**保证的，不是靠记得加 `if`；频繁切 `WS_EX_TRANSPARENT` 会让画面抖

代价是控制区外一圈 24px 的环里点击不会穿透。这是**有意为之**的取舍：
那圈里误判成"可点"只是浪费一次点击，误判成"穿透"却可能真的误操作到别的东西。

另外，**收起态（只剩那一条栏）时整窗都是控制区，永远不切穿透** ——
否则用户把窗口收起来之后，连"展开"这个按钮都点不到了。

#### 上报的必须是「一组矩形」，不能是它们的包围盒

这是穿透功能**一开始整个不生效**的原因，值得单独记一笔。

前端要把"控制区长什么样"告诉后端，因为布局只有 DOM 知道（设置抽屉开着、
历史浮层展开着、收起态下都不一样）。最初的做法是把所有 `[data-interactive]`
元素的 `getBoundingClientRect()` 求一个**包围盒**，只上报一个矩形。

问题在于当时控制栏有**两块**（顶部那条栏 + 底部控制台）。两块的包围盒恰好覆盖**整个窗口**
—— 于是后端算出来"光标永远在控制区里"，穿透**一次都没触发过**。
而它的表现很像"功能没实现"：开关点得动、状态也显示，就是鼠标照样被窗口挡住。

> ★ 2026-09-26 两条栏并成一条之后，这个特例本身不会再发生（栏的包围盒就是栏）。
> 但**这条纪律没有因此失效** —— 只要上报的元素超过一块、而它们分散在窗口两侧
> （顶栏 + 设置抽屉 + 历史浮层就是这个形状），包围盒就会再次盖满整窗。
> 所以代码里仍然是"一组矩形"，不是"一个框"。

改成逐个上报（`[left, top, w, h]` 的数组），后端对**每一个**矩形分别判
"在不在里面 / 在不在外扩环里"，任一命中即可点。

配套加了两条守卫，都是"宁可多挡一下也不能点不动"的方向：

* `sanitize_zones` —— 空数组 / 超过 32 块 / 含 NaN / 宽高 ≤ 0 一律判为脏数据，
  退回"整窗可点"。判断错了只是多挡一次点击，判成"整窗穿透"却可能让用户点不到任何东西。
* **没收到可交互区时强制切回可点**。原先这条路径是"保持现状"，
  于是一旦上报中断，窗口会**留在穿透态**。现在它会主动退出来，并在日志里说明一句。

#### 收集可交互区要判「几何可见」，不能只判 `offsetParent`

改成一组矩形之后它**仍然**没生效，这是第二个、也是更隐蔽的原因。

收元素的代码当时是这么滤的：

```js
.filter((el) => el.offsetParent !== null || el.getClientRects().length > 0)
```

看起来没问题，但它漏掉了一类元素：**靠 `transform` 挪出窗口的浮层**。
设置抽屉（`.drawer`）是常驻挂载的，关着的时候只是 `transform: translateX(101%)` ——
它 `offsetParent` 依然非空、`getBoundingClientRect()` 依然老老实实给出一块 352×358 的矩形。
于是它被当成第三块「可交互区」报了上去，把窗口右侧一整条误判成"可点"。

（其余浮层 —— 查找栏 / 历史 / 粘贴弹窗 —— 关闭时都是 `return null`，只有设置抽屉是常驻的。
所以只有它出问题，这也正是它难被发现的原因。）

正解是把判据换成**几何**的：算完矩形之后，检查它跟视口有没有交集，
并且把矩形**裁进视口**（伸到窗口外的部分在物理坐标里没有意义）：

```js
if (right - left <= 0 || bottom - top <= 0) return null;   // 完全在窗口外
```

顺带补了 `display:none` / `visibility:hidden` / `opacity:0` 三条 ——
它们都是"元素还在、但用户看不见"，都不该算控制区。

**同时修掉了一个静默失败**：上报调用原先写的是 `.catch(() => {})`。
后端的兜底是"没收可交互区就永不切换"，两者叠加的结果是
—— 上报链路断掉时，界面上只剩"穿透开关点了没反应"，没有任何线索指向真正的原因。
现在第一次上报失败会直接弹一条警告，后端也在收到/形状变化时落一行路标日志：

```
[click-through] 可交互区已更新 → 2 块 @ 1506,219 978×81 | 1506,300 978×53
```

这行日志是穿透失效时的**第一现场**：没有它 ⇒ 断在前端；有它但形状不对 ⇒ 断在 DOM 标了哪些
`data-interactive`。只在形状变化时记，所以 400ms 一次的轮询不会把日志冲成一片噪声。

### 穿透的"可交互区"边界到底在哪（量出来的数字）

`APPROACH_PAD = 24` 是**屏幕物理像素**，不是 CSS 像素 —— 这条容易被忽略，
因为它只在非 100% 缩放的机器上才显形。在本机（缩放 1.75）⇒ 约 **13.7 CSS px**。

★★ **2026-09-26 起只有一条栏** —— 两条栏并成一条之后，底部那 82px 的控制台整个取消，
于是可点区从"上下两块"变回**顶上一条**，其余（稿件区直到窗口底）全是穿透的。
记窗口高度为 `H`，则：

| 量 | 距窗口顶（CSS px） | 来源 |
|---|---|---|
| 栏（唯一一条，贴窗口最上方） | 0 – 46 | `--h-top: 46px` |
| 栏的接近环 | 46 – 59.7 | 46 + 24 ÷ 1.75 |
| **（稿件区）** | 59.7 – `H` | ⇒ 这一段**穿透** |
| ~~底部控制台~~ | **无** | `--h-cb: 0px`（栏已并成一条） |

★★ **栏的条数也必须是现读的，不能写死"上下两条"。**
`--h-cb: 0px` 就是"窗口底部没有栏"的意思。脚本如果还照着老版面算一条底部期望带，
就会把"底部能穿透"（这**现在正是正确行为**）报成失败 ——
又是一个跟穿透毫无关系的假警报，而这条脚本的注释反反复复就在防这一类错。
（真踩：合并栏之后第一次跑 `--expect-bars` 之前先改了这段逻辑。）

★★ **期望值跟窗口高度绑在一起** —— 而窗口高度是用户拖出来的
（本机配置里存的就是 **274**，不是默认的 360）。
写死一个区间（改版前的 `"0-88"`，或按 360 高窗口算的 `"0-61,263-360"`）**必然失败**，
而失败原因跟"穿透坏了"无关，纯粹是版面/窗口高度变了 ——
那种"红得没道理"的报错最费时间，也最容易被误判成功能坏了。

所以脚本从**唯一源**现算期望值（栏高读 `styles.css`、接近环读 `click_through.rs`
的 `APPROACH_PAD`、栏的条数看对应的 `--h-*` 是不是 0）：

```bat
python scripts\verify-click-through.py --step 4 --expect-bars
```

真机实测（窗口 560×**274**，缩放 1.75）：

```
版面常量：--h-top=46 --h-cb=0 APPROACH_PAD=24物理px ÷ 1.75 = 13.7css ⇒ 顶栏（底部无栏）
实测「可点」区间（CSS px，距窗口顶）：0-60
期望「可点」区间：0-60
✅ 剖面与期望一致
```

★ 同一台机器上这条命令还抓到过一段 `248-260` 的空洞，**再跑一次就没了** ——
真机扫描本来就有噪声（有人动鼠标、窗口偶尔被挪）。脚本现在把这种"期望区间内出现穿透"
单独报出来（退出码 2）并提示重跑，而不是直接判失败：
**复现就是真的，不重现就是噪声**。

★ 另有一条判据上的讲究：期望区间**两端 ± 一个容差**内的采样点判为「不关心」。
扫出来的剖面是离散的（步长 4css），边界只能分辨到一个步长以内，
把边界附近也强判成"必须可点"会让 1px 的期望误差放大成 8px 的假警报
（第一次跑就报了 64/68 两处"不一致"，纯属容差自己造出来的）。

### 穿透必须配一个托盘，否则等于把窗口锁死

穿透态下窗口不接收任何鼠标消息，右键菜单也出不来。此时如果只能靠改配置文件才能退出，
这个功能就是**不可撤销的**。所以托盘不是"顺便加的功能"，而是穿透的**安全前提**：

- 场景 1：用户忘了穿透开着，鼠标怎么点都没反应 → 托盘右键「取消鼠标穿透」
- 场景 2：穿透 + 全局热键被别的软件占用 → 托盘是唯一还能触达的入口

托盘菜单里带**最近 5 篇稿子**，是因为会议前最常见的动作是"换一份稿"，
而那时窗口可能正折叠着、或正穿透着 —— 从托盘直接切，比先恢复窗口再去点历史快一步。

### 一条栏贴在窗口最上方，图标用 SVG 而不是字形

布局定成：**唯一的一条栏贴窗口最上方（46px）**，`position: absolute` 浮在正文之上
（`bar_pinned`）—— 正文因此**从栏的下方开始**。关掉「顶栏浮在正文上」之后它回到普通流，
占独立一行，连第一行都不挡。窗口底部**没有栏**，正文一直铺到底。

★★ **栏搬过家，变量名必须跟着搬** —— 这是维护陷阱，不是洁癖：
   更早的版本是"顶栏 + 底部进度条"（`--h-bottom` → `--h-prog`）；
   上一轮进度栏搬到窗口底部、长成了两行的"控制台"（`--h-cb: 82px`），
   顶栏下沿那条细进度线另叫 `--h-topline: 2px`。
   **2026-09-26 把多条栏并成一条** ⇒ `--h-cb: 0px`（＝"底部没有栏"）、
   `--h-topline` 整个删掉（进度线本身没了，改成栏里那条**可点**的进度条）。
   **名字与位置对不上，下一个人会去错的地方找那条栏，然后以为它被删了。**

搬迁时最容易漏的是三处"只改一半"的地方，症状都很怪：

| 漏了什么 | 症状 |
|---|---|
| 只改 `top`，没把 `bottom: 0` 清掉 | 上下同时被钉住 ⇒ 那条栏被**拉成满窗高**，把稿子整片盖住 |
| 稿件区的内边距没跟着版面走 | 第一行稿子**藏在栏后面**；或底部空出一大块（旧版留给控制台的地方） |
| 锚定到栏的浮层（历史 / 查找）没跟着走 | 浮层被栏**压掉一截**（浮层 z-index 更高，会盖在栏的上面） |

`App.tsx` 里这条栏是常驻渲染：钉住态下它是 `position: absolute`；
但关掉「顶栏浮在正文上」之后它回到普通流 —— **顺序就决定了谁在上面**。

图标从 `⌕ ✎ ☰ ▾ ⚙ ─ ✕` 这类 Unicode 字符换成了内联 SVG，理由是**字形渲染不可控**：
`⌕`(U+2315) 在 Windows 上渲染成一个带尾巴的小圈（根本不像放大镜）、
`✎`(U+270E) 渲染成一根斜杠；而且这几个字符来自不同 Unicode 区块，
字重、视觉大小、基线全不一致，一排过去像临时拼的。SVG 一次解决全部问题：
同一条 `viewBox`、同一个 `stroke-width`、颜色取 `currentColor`（hover 变色天然生效），
尺寸由 width/height 精确控制 —— **不受字体影响**，也不存在"这台机器缺哪个字形"。

还有一条非改不可的理由：**字形跟着 `font-size` 变形**。顶栏这一轮要放大，
字号一动那几个字形就跟着走样，而 SVG 不会。

#### 560px 下标题刚好放得下；有警告或有调速条时整块让位

宽度预算是这一行最紧的一环。**把顶栏从「4 个文字胶囊 + 7 个图标」砍到
「1 盏状态灯 + 5 个图标」**，是"简化"最实在的收益 —— 它换回来的不是好看，
而是**标题终于放得下**（改版前它被挤到 `titleW=0`）。

★ 合并成一条栏之后这笔预算又被摊薄了（同一行里多了推进组、位置、进度条），
所以这一轮把能做小的定宽项都做小了：图标 32→30、间距 4→2、
推进组内距 2→1、胶囊内边距 9→8。**实测（560×274，`--measure`）**：

| | 定宽项合计 | 标题（`--measure` 实测） | 进度条 |
|---|---|---|---|
| 并成一条栏（未收紧） | 362 | `titleW=93`（差约 23px，被省略号截断） | 52（压到下限） |
| **收紧后** | 352 | **`titleW=116 · titleTextW=115.7 · titleShort=-0.6`** | 61 |

★★ **这里能动的只有"定宽项"**：标题 + 进度条 = 行宽 − 定宽 − 间距 − 内边距
（实测 560px 下约 175px），`flex-grow`、比例、`min-width` 都改不动这个总数，
只能改两者怎么分。所以"给标题让地方"的唯一办法是把定宽的东西改小。

★ 实测口径有个坑：`titleClip` 曾写成 `scrollWidth > clientWidth + 1`，
在"就差 0.5px"这种边界上它会**报反**（截图明明挂着省略号，它说没截）。
现在换成用 `Range` 量文字的真实排版宽度、直接报 `titleShort`（差多少 px）。

**两个状态会让标题整块退场**（`.topbar:has(.tb-status) > .title` 等）：

| 状态 | 不让位会怎样（实测） |
|---|---|
| 状态槽有话说（警告 / 错误 / 穿透未生效…） | 标题与警告**双双被压残** |
| 匀速滚动**正在跑**（那一格换成调速条） | 标题只剩 **60px**（`titleShort=55.7`）—— 一个 "2026…" |

判据是"这三者里谁必须现在看"：警告必须、调速条次之（那一刻你的眼睛在正文上，
盯这条栏看的是"走到哪了、要不要加速"），标题最不急 ——
"我在念哪份稿"在正文里、在「稿件」浮层里、悬停元素本身都看得到。

★ 这个让位规则 2026-09-27 改过一次：原先**只**认状态槽，理由是"调速条是正常控件，
凭什么让标题消失"。那个判断是在**假图上**做的 —— 预览工具当时让截图比真实窗口宽
32px，于是以为还能剩 90px，修掉工具后实测只有 60px。（详见"离线预览"一节。）

`minWidth` 保持 **540**：窄过它标题整块隐藏（`@media (max-width: 540px)`），
而不是让它被挤成 "2026…" 那样一小截 —— 那既没告诉你这是哪篇稿子，
又显得界面没做完，比不显示更糟。

### 状态自己说话，而不是弹一段字

这一轮把「隐身」做成顶栏**一盏状态灯**（盾牌图标 + 3 个字），
把「演示 / 跟读」做成中央那枚**大圆按钮**，同时删掉了操作后糊上来的长句提示。
判据是同一条：**能用界面状态表达的，就不要用文字复述。**

★ 为什么隐身不再是一个 4 字长胶囊：顶栏原先并排着 4 个文字胶囊
  （投屏隐身 / ▶演示 / 穿透 / 锁定），一共吃掉约 518px，把标题挤到 `titleW=0`。
  现在只留**每场直播都要确认三遍**的那一个、压成"图标 + 3 字" ——
  五态：`未隐身 / 隐身中 / 已暂停 / 未生效 / 不可用`。

#### 隐身：两态不够，因为「暂停」不是「关掉」

后端只有 `hidden | visible` 两个模式。但用户心里有三件事：
「没用它」「临时把窗口露给观众看、等下还要回来」「不用了」。
少了中间那层的后果很具体：**演示中途不敢点** —— 点一下就从"隐身中"掉成"未开启"，
想回去只能当成重新开启，而那一刻正是最不能分心的时候。

所以前端单独存 `stealthIntent: "off" | "on" | "paused"`，与后端回报的事实
（`stealth`）分开。第三态是**前端推出来的**：

* 后端报 `hidden` ⇒ 意图 `on`
* 后端报 `visible` 而原本意图是 `on` ⇒ 这是**暂停**，不是关掉
* 显式点击的先设意图再发命令，所以点击路径不受这条推断影响

最后一条很关键：热键和托盘的切换没有返回值语义，只能靠"事实变了"反推 ——
推断写反的话，演示中途按一下热键，界面上就只剩「重新开启」，再也找不到「继续」。

**「彻底关掉隐身」刻意不放在这盏灯上。** 它是设置项（启动时自动隐身）。
放在灯上会让人在演示中途手一抖把保护撤掉 —— 而且分不清"我暂停了一下"
和"我不用它了"。暂停之所以必须是独立一态，正因为它**可逆、有记忆**；关掉不是。

四态与配色（一个颜色只能有一个意思）：

| 态 | class | 颜色 | 说明 |
|---|---|---|---|
| 投屏隐身 | `.on` | 绿 | 点与呼吸点都在动，扫一眼就能确认 |
| 开启中 | `.starting` | 绿 + 扫光 | 已下指令、等后端确认 |
| 已暂停 | `.paused` | **蓝（accent）** | 用户自己按的，是正常操作，不是问题 |
| 未生效 | `.warn` | 琥珀 | 下了开启指令却没生效（最不能出错的一态） |
| 未隐身 | `.off` | 灰 | |

琥珀在这条栏里**只归"受限 / 没生效"**。暂停用琥珀会让人以为出了故障，
然后去查一个不存在的问题。

#### 「开始提词」：一个主角按钮，四态

★★ 这是本轮改版的核心动作 —— **把两个"开始"合成一个**。
改版前顶栏有「▶ 演示」、设置里有「开始识别」，两者都能让跟读跑起来，
用户分不清差别，而且两边状态会不同步（一边开了、另一边不知道）。

现在**常驻界面上只有底部控制台正中那一个大圆按钮**；顶栏那个「▶ 演示」胶囊摘掉了。
设置 › 提词 里仍留着一个「开始 / 结束」，但它和按钮**走同一份编排**
（`lib/prompting.ts`，全应用唯一一份），所以两处的状态永远一致 ——
它只是"人在设置里时不用先关掉设置"。四态（`promptState`）：

| 态 | 外观 | 点它会做什么 |
|---|---|---|
| 就绪 | **绿描边** + ▶ | 开始提词：隐身 + 置顶 + 按当前**推进方式**开始（语音跟随 / 匀速滚动），一次做完 |
| 就位中 | 扫描动画 | （禁用）等后端确认 |
| 提词中 | **实心绿** + ⏸ | **暂停**：只停推进，隐身与置顶原样保留 |
| 已暂停 | **蓝描边** + ▶ | 继续：把推进接回来 |

★ 「就绪」与「已暂停」画的是同一个 ▶，于是**只能靠颜色/边框区分**：
  就绪是绿描边（正常）、暂停是蓝描边（用户自己按的）。
  ⇒ 验收时一定要量 `borderTopColor`，不能只量 `color` ——
  第一版把两者做成了逐字节相同，肉眼也分不出。

★★ **匀速滚动会自己走到头**，那不是一个第五态，而是回到「就绪」：
大圆按钮变回绿描边 ▶（再按一次从头重滚），控制台那一格显示绿色「已讲完」。
两处**必须同时变** —— 只说一半的话（控制台说了、按钮还亮着实心绿），
人扫一眼屏幕只会看那个大按钮，于是以为它还在滚，其实早停了。
这就是"界面显示实际在工作，不是用户按下的意图"的反面。
实现上由 `state.demoEnded` 这一维承载：不用 `demoActive === false` 顶替
（那条路上"讲完了"和"讲到一半被停"是同一个值，前者该说「已讲完」、后者什么都不该说），
也不用"光标在末尾"顶替（把进度条拖到底也会到末尾，那会儿他什么都没讲）。

**收摊**（停跟读 + 撤置顶）**不在这个循环里**：它是演示的终点、不可逆、低频，
所以收进「设置 › 提词」。与隐身「彻底关掉放设置」是同一条约定：
**可逆的、高频的留在按钮上；不可逆的、低频的收进设置。**

暂停与收摊**都不动隐身** —— 隐身是用户自己的开关，
顺手撤掉会造成一种很难察觉的后果：以为讲完了就安全了。
要临时把屏幕给观众看，顶栏那盏灯上的一下「暂停」就在手边。

编排收在 `lib/prompting.ts`（全应用**唯一**一份），大圆按钮、设置页都调它 ——
各写一份，迟早会出现"按钮那个开了隐身、设置里那个没开"这种只在真会议上发现的差异。

#### 「跟读」组：讲的过程中会想调的那几件事

新增一组「设置 › 跟读」，装的是**一边讲一边也可能想动**的手感项。
判据与常驻栏同一把尺子：不是"它属于哪个功能"，而是"一场直播里会碰几次"。

| 项 | 控件 | 落到的真实参数 | 出厂值 |
|---|---|---|---|
| 跳读范围 | 绿滑块 1–40 | `AlignConfig.forward/backward`（对位引擎搜索窗口） | 20 句 |
| 跟读位置 | 绿滑块 15–60% | `config.anchor`（原来埋在「更多›高级排版」里） | 36% |
| 跟读颜色 | 7 枚色点 | `config.read_color` → CSS 变量 `--read` | 绿 |
| 平滑滚动 | 开关 | `config.smooth_scroll` → `scrollTo behavior` | 开 |
| 快捷跳读 | 开关 | `config.quick_jump` → 正文单击跳 / 双击跳 | 开 |
| 跟读灵敏度 | 绿滑块 | `config.match_floor`（从「提词」组搬来） | 0.38 |

★ **每一项都必须有行为落点**，不接受"做了个长得像的开关"。
本轮唯一的引擎改动是「跳读范围」，而它的出厂值 20 句换算出来是
**240 字 —— 与引擎此前的硬编码窗口逐字相同**：
接出这条滑杆不改变任何出厂手感，只是让它**可调**。
`align::tests::jump_window_preserves_legacy_defaults` 把这件事钉住了。

★ **「关掉」与「禁用」是两件事**。快捷跳读关掉之后**不是点不动了**，
而是把单击改成双击（防手抖点飞）—— 所以那一行的副标题会跟着换成
"已关：改成「双击」才跳"，否则用户只会得出"这个点不了了"的结论。
这条与穿透的"删文案前先确认失败信号还有别处承载"是同一条纪律。

★ **颜色分家**：跟读指示色走 `--read`（默认绿），而 `--accent`（蓝）
留给"用户自己按下的东西"（暂停、查找命中）。此前两者共用 accent，
于是"我念到哪"和"我刚点了哪"在屏幕上是同一个颜色。

★ 色板有**两套值**（深色 / 浅色）：这几个色是按深色背景挑的高明度色，
放到浅底上做 2px 下划线几乎看不见。它**不能**靠 CSS 主题块覆盖 ——
`--read` 是内联写在根元素上的，内联优先级更高 ⇒ 只能由 JS 按
**解析后的主题**选（`system` 要先解成实际的）。
浅色档与既有 `--ok` 同值（绿：深 `52 211 153` → 浅 `5 150 105`），是成套的档位而不是随手挑的。
验收要两套都量：深 `readVar=52 211 153` / 浅 `readVar=5 150 105`。

★ 跟读组的滑块是**绿的**，其余组仍是蓝的 —— 同一个意思只用一个颜色，
反过来也一样：**一个颜色只承载一个意思**。

#### 穿透：入口收进设置，但**失败信号一个都不能少**

穿透是"会关掉某个输入通道"的能力，所以它的两件事必须**分开数**：
**退出口**和**失败信号**。

**退出口（三条，一条都不能少）**：设置 › 窗口 的开关、托盘菜单、热键 `Ctrl+Alt+P`。
本轮把顶栏那个文字胶囊摘掉、换到设置里，这三条都还在。

**失败信号**：改版前靠顶栏胶囊"宽限 2.2s 后变琥珀"。收进设置之后，
它一度**没有任何地方承载**（`ctPending` 成了没人读的死状态）——
用户按热键开穿透（人还不在设置页）、后端判它没生效，界面上**什么都不会发生**，
正好退回"点了没反应"。现在它挂在**底部控制台第一行那个唯一的状态槽**上：

| 瞬间 | 表达 |
|---|---|
| 刚点下 | 开关自己进入"开启中"（宽限期内不报警） |
| 已生效 | 开关亮起；状态槽回到正常的剩余时间 |
| 开了但迟迟没生效 | 状态槽出现琥珀 `穿透未生效 · 点击查看`（宽限 2.2s 才亮，免得正常切换也闪警示色） |

判据用 `ctPending && !ctActive`（意图已下、后端没确认），**不是** `!ctActive` ——
后者在"压根没开"时为真，会常年挂一条假警告。

这条信号按**实际在工作**判，不是按用户意图 —— 后端 `ct_working()`
（`ct_enabled() && zones_ok()`）。**不能拿 `ct_now()` 驱动它**：
它表达的是"此刻光标在不在稿件区"，鼠标一动就翻，会闪成一片，
而且分不清"功能没生效"和"光标恰好在栏上"。

状态怎么收敛：后端 40ms 轮询线程检测到 `ct_working()` 变化就
`emit("prompter://click-through", working)`，前端 `events.onClickThrough` 收下 ——
所以"点了之后可交互区才报上来"这种情况，灯会自己变绿，不需要再点一次。

#### 删长文案的边界：确认类可以删，警告类只能"换个地方待着"

删掉的是**确认类**（"已切换主题""已锁定""已全屏""已载入 XX 字"）——
这些在界面上本来就有对应变化（图标翻了、按钮文字变了、稿子换了），
再用一句话复述一遍只是噪音。

**没有删的是警告类**，因为它们表达的是"界面状态说不出来的事"，典型是
「历史已清空，但你的原始文件一个都没删」。它的处置是**从"操作后强塞的弹窗"
移到"就地可查的位置"**：历史浮层底部本来就有一行常驻说明写着
「只删历史与副本，不动你的原文件」—— 那是**点之前**就看得见的，比事后一句更早。

判据是：**不弹它会不会出事。** 会出事的（隐私、丢文件、以为开了其实没开）留下，
只是换个更早、更安静的位置；不会出事的删掉。

#### 控制台那条常驻状态的标签，必须由生产者给

这条通道原先把标签写死成「麦克风异常 · 点击自检」。可它现在有**六个以上**的生产者
（麦克风送数字静音、穿透可交互区上报失败、隐身没生效、跟读失准、穿透没生效、
收摊没停干净…），写死的标签于是会**说假话** —— 隐身没开却显示"麦克风异常"，
比不提示更坏：它把人引到错的地方去查。

改成 `StatusWarning { label, detail }`：`label` 是铺在栏上的短句（生产者负责短），
`detail` 放 `title`（长成什么样都行）。

★ 本轮把它收紧成**一个位置、五个生产者、按优先级依次占用**
  （见 `ControlBar::statusLine`）：
  错误 > 后端警告 > 穿透没生效 > 跟读失准 > 剩余时间。
  不是并排挤成一小堆，而是让更要紧的那个把位置占掉 ——
  这跟"一个颜色只能有一个意思"是同一条纪律：**那一行也只能有一个意思**。

### 稿件库：文件只记路径，粘贴的才存副本

历史列表要记住"用过哪些稿"，但**不能把用户的文件复制一份进程序目录** ——
用户改了原稿（比如临开会前改了个数字），点历史却加载出旧内容，这是比"没有历史"更坏的结果。
所以：**从文件导入的只存路径**，列表里如实显示"文件已被移动/删除"；
**粘贴进来的才存副本**（它没有别的落点，不存就真丢了）。

去重键用 **FNV-1a 哈希**而不是 `DefaultHasher` —— 后者不保证跨 Rust 版本稳定，
换个编译器重新构建，"同一篇稿"就会算成两篇，历史列表开始出现重复项。

淘汰策略是**保留有主的最久 50 篇**：被"钉住"的（当前正在用的）永不淘汰，
免得好不容易攒起来的历史被一次批量导入冲掉。

### 拖入稿件：一个"承诺了却静默失败"的功能

顶栏空态里一直写着「把 .txt / .md 拖进来」。但窗口开着 `dragDropEnabled: true`
（默认值，为了让系统把文件**路径**交给我们），Tauri 会**劫持**拖放、
只发自己的 `tauri://drag-*` 事件 —— 前端那些 HTML5 的 `onDragOver` / `onDrop`
**永远不会触发**。

结果就是：文案承诺了拖放，用户真的拖了，什么也没发生，控制台零报错。
这是最坏的一类 bug —— **界面在撒谎**。修法不是在文案上退让，而是把 Rust 侧的事件接上，
并让三种失败都**说出来**：格式不支持（且告诉用户 `.doc`/`.ppt` 该另存为什么）、
读了但解码失败、拖了多个文件。

### Word / PPT 导入：手写扫描器，而不是引一个 XML 库

`.docx` / `.pptx` 都是 ZIP 包着一堆 XML，抽正文只需要"认出哪些元素是正文文本、
哪些是段落边界"。这件事有两条路，这里选了"看起来更土"的那条：

* 引 `quick-xml` 之类的库 —— 通用、能处理畸形输入；
* 手写一个按 `<` 切分的扫描器 —— 二十行，行为完全可控。

选后者，理由是**可验证性**：手写扫描器是纯函数（吃 XML 字符串、吐纯文本），
所以"多个 run 要拼在同一行""`<w:br/>` 算换行""`&#65;` 要解成 `A`"
这些判断全都能脱开真实的 Office 文件写成断言。而引库的话，
"库在这个边界上怎么表现"就成了我们**没法单测**的外部行为。

能这么切的前提是 Office 生成的 XML 里，正文中的 `<` 一定被转义成 `&lt;` ——
所以文本节点里不会再出现 `<`。这一条写在代码注释里，因为它一旦不成立，扫描器就错了。

两个刻意的取舍：

* **PPT 优先取备注页，没有备注才退到幻灯片正文。** 讲稿在备注里，
  幻灯片正文往往只有标题几个字 —— 提词器要念的是备注。
* **排掉备注页里的"幻灯片编号"字段**（`<a:fld type="slidenum">` 里也有一个 `<a:t>1</a:t>`）。
  不排的话每页正文前面都会多出一个孤零零的数字行。
* `.doc` / `.ppt` 老格式**不做**。那不是 ZIP 而是 OLE 复合文档，解析成本远高于收益，
  报错里直接告诉用户"另存为 .docx"。

加 `zip` 依赖时用了 `default-features = false, features = ["deflate"]`：
默认特性会拖进 aes / bzip2 / lzma / zstd / zlib 一整排解压后端，
而 Office 文件只用 deflate —— 多带的每一个都是白编译的代码与白背的攻击面。

### 稿内查找：只"看"，不"跳"

查找和跳转是两件事，混在一个动作里会互相破坏。

会前翻稿子找"Q&A 那一页"，如果每按一次「下一处」都把朗读光标搬过去，
用户找完一圈之后就**已经不在原来念的地方了** —— 找位置这个动作本身把位置弄丢了。

所以按下 Enter / 点 ↑↓ 只做"滚过去 + 标出来"，朗读进度一动不动；
真要从此处开始念，有独立的「从这处开始读」按钮，那一下才动光标。
把两个意图分开，用户不需要猜"我刚才那下算不算跳转"。

配套的两个小决定：

* 查找打开期间**关掉自动滚动**。否则用户刚翻到某处，语音一推光标又把画面拽走了。
* 命中计数与稿件区高亮**共用同一个 `findHits`**（`src/lib/find.ts`）。
  两处各算一遍必然在"大小写怎么算""空查询怎么办"上分叉，
  表现是"数着 12 处、只标出 11 处"，极难查。
* 用 `indexOf` 而不是正则：搜 `(` `[` `.` 这类字符不该需要先学会转义。

### 编辑稿件：只另存副本，绝不改用户的原文件

在应用里改稿子，保存时走的是 `set_script_text` —— 落一份历史副本，
**原文件一字不动**。理由是用户可能只是想为这次演讲调整措辞，
不该顺手改掉硬盘上那份 Word。界面上直接把这句话写出来，不靠用户自己推测。

### 尺寸记忆：越界一律**回落默认值**，而不是夹到边界

窗口尺寸存进配置后就有了"被写坏"的可能（手改、断电写坏）。0、99999 这类值只可能来自
损坏，此时我们**并不知道用户想要什么**。夹到下限会得到一个能开但几乎没法用的窗口
（比如高度 160 只显示两行字，读稿时会因为频繁滚动而晕）；回落到一个有论证的已知良好值
（560×360）则至少是能用的。两个坏选项里选更好那个。

位置的自愈同理：判定"还在不在屏幕里"用的是**重叠区域宽高都 ≥ 80px**，
而不是"左上角在屏内" —— 后者在窗口大部分移出右侧时会误判为可见，
而用户其实一个按钮都点不到。**副屏在主屏左侧时的负坐标是合法位置**，
必须原样保留，否则那类用户每次重启窗口都会被拽回主屏。

### 麦克风没声音时，程序必须自己说出来

这一条来自一次真实故障，也是整个项目里最值得记住的一课。

**现象**：点了「开始识别」，光标一动不动。日志里一片祥和。

**排查结果**：那台笔记本的麦克风阵列在系统里显示 `ACTIVE`、未静音、音量 82.5%，
但驱动送出来的全是**恒定近零值**（-113 dBFS —— 真实麦克风哪怕深夜安静房间
也有 -60 dBFS 以上的本底噪声）。用三套彼此独立的录音实现（我们自己的 `cpal`，
以及跟本项目毫无关系的 PortAudio 的 WASAPI / DirectSound / MME 三个后端）各测一遍，
结果一致：**四声道峰值逐位相同**，说明驱动的阵列处理通路被关掉了。

也就是说，代码里**每一步都成功**：流打开了、回调按额定速率送数据、解码器正常输出。
唯一的问题是拿不到声音 —— 而这一点在界面上**完全没有痕迹**。用户能得出的唯一结论是
「这软件是坏的」。

这是最糟的一类失败：**静默失败**。所以修法不是「修好麦克风」，而是三条：

1. **加一条非致命警告通道**。原先 `AsrUpdate` 只有 `error`，而它的语义是"引擎已停止"。
   麦克风无声时引擎没停，塞进 `error` 会让界面显示「已停止」，用户会去重启识别 ——
   当然不解决。所以新增 `warn` 字段，走独立的 `prompter://warning` 事件，
   控制台用黄色而非红色，并且**带上「怎么办」**。
2. **加电平心跳**。原先只有识别文本变化时才推送事件 —— 麦克风一旦无声，
   文本永远不变，界面就再也收不到任何更新，连警告都送不出去。现在文本不变也按
   250ms 推一次电平，主角按钮外圈的呼吸环因此始终反映真实状态（改版前是底栏一根小电平条）。
3. **把判据抽出来单测**。判定阈值错了线上不会报错，只会在真开会时冒出一条误报，
   所以它必须能被测试钉住。

**静音阈值的取法**（这是全项目最需要解释的一个数）：

| 来源 | 电平 |
|---|---|
| 死设备：围绕某常数的**量化噪声**（16bit，1 LSB ≈ -90 dBFS） | **-138 ~ -83 dBFS**（实测浮动范围） |
| 真实麦克风：深夜安静房间的**声学底噪** | -70 ~ -60 dBFS |

阈值取 **-80 dBFS（`DIGITAL_SILENCE_PEAK = 1e-4`）**。

注意上面第一行那个 55dB 的浮动范围 —— 它本身就是「这不是声学信号」的证据，
同时也说明**阈值不能定得太低**：最初的实现取 -100 dBFS，于是同一个故障设备
在两次测量里一次被判「静音」、一次被判「有信号」，自检和实时链路互相打脸。
这个不一致是被端到端测试 `watchdog_sees_dead_microphone` 抓出来的，
而那条测试断言的正是**两条链路结论必须一致**这个不变量。

方向不要搞反：往上调是危险的（会吃掉真实房间的底噪，导致每次开会都误报），
往下调则只是漏判。

### 识别引擎可插拔，本地优先

| | 本地离线 | 云端 |
|---|---|---|
| 术语 / 人名准确率 | 一般 | 明显更好 |
| 断网 | 不受影响 | 不可用 |
| 隐私 | 音频不出本机 | **汇报语音上传到第三方** |
| 成本 | 0 | 按量计费 |

默认走本地。云端引擎的接口（`asr/cloud.rs`）已经立好，接具体服务时只需要补那一个文件，
不需要动对位、UI 和状态机。

### 三种推进方式：谁决定稿子往下走

设置 › 提词 的第一行是一个三选一。它取代了原来那个叫「引擎」的单一下拉框 ——
那个框把「用不用麦克风」和「用哪个语音模型」混成一个控件，于是"我想让稿子自己滚"
这件事在界面上没有位置，用户只能去猜一个叫 `Manual` 的东西是什么意思。

| 推进方式 | 靠什么往前走 | 要麦克风 | 典型场景 |
|---|---|---|---|
| **语音跟随** | 识别结果与稿件对位 | ✅ | 脱稿讲、稿子只是提纲 |
| **匀速滚动** | 一个时钟：`base + 经过时间 × 速度` | ❌ | 稿子念得很熟；不方便戴麦；要卡时长 |
| **纯手动** | 你自己按上一句 / 下一句 | ❌ | 逐条念、随时插话 |

选「语音跟随」时会多出「来源」与「模型」两行（在 **设置 › 更多 › 语音跟随**）；
选另外两个时那两行整节不出现 —— 不碰麦克风的模式里摆一个用不上的模型选择，
只会让人去查一个不存在的问题。同理，「会前自检」在非语音模式下会把麦克风与模型
两项直接标成「跳过」，而不是报一个假的红。

**匀速滚动的四个实现口径**（都有代价，改之前先看这条）：

1. **位置在后端线程里按时间现算，不是前端定时器，也不是逐拍累加。**
   投屏时提词窗口通常不在前台，浏览器会把 `setInterval` 节流到 1s 一拍，真机上就是
   "一卡一卡地跳"；而逐拍累加会随每拍的误差漂移，十分钟偏出一大截。
2. **落位走一条独立通道**（`AsrUpdate.seek`），不送进文本匹配。
   匀速滚动的位置是**算出来的已知答案**，再让对位器猜一次，稿里一有重复句就会猜错，
   把光标甩到别处。
3. **中途调速会先把当前位置冻住当新基准**（`Rate::rebase`）。
   不这样做，调速那一刻光标会跳一段 —— 新速度乘上"已经过去的总时长"。
4. **改「推进方式」不重启正在跑的引擎**，下次开讲才生效（设置页里写明了）。
   中途换引擎必然让画面卡一下，而用户多半只是在确认自己设对没有。

讲的中途要调速不必回设置：控制台第一行那一格在开讲后会**让给一条速度条**
（60–600 字/分）。那一格平时显示的是"还要讲多久"，而速度正是"还要讲多久"的唯一变量。
滚到底时它会变成绿色的 **「已讲完」**，中央大圆按钮同时回到「▶ 开始提词」——
再按一次会从开头重滚一遍。
