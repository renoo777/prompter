### 4. 自动化验证「隐身」是否真的生效

除了人眼看，还可以让脚本给出客观证据 —— 改完代码回归验证时尤其有用：

```bat
python scripts\verify-stealth.py
```

**先说两个必须知道的坑，否则一定会误判：**

1. **应用默认就是隐身的**（配置项 `stealth_on_start` 默认 `true`）。所以一张
   「刚启动的应用」的截图里它本来就不该出现。判断隐身有没有生效**必须靠切换前后对比**，
   靠单张图是没有意义的。
2. **期望的不透明度要从应用自己的 `config.json` 读**，不能拿默认值硬比。
   设置抽屉里的滑杆一改就落盘成 `"opacity"`。这条踩过：脚本硬编码默认的 0.94，
   而配置里写着 `0.3`，于是把「应用忠实地按 30% 渲染」误报成「透明度算了两遍」。
   现在两个脚本都会自动读这个文件，并打印出期望值来自哪里。

`verify-stealth.py` 的做法是：先用 `Ctrl+Alt+H` 把窗口整个藏起来截一张**锚点图**
（此时捕获到的必然是纯背景），再各按一次 `Ctrl+Alt+S` 截两张候选图。有了锚点：

- 两张候选图里，跟锚点几乎一致的那张 = 窗口被排除出捕获的那张；
- 另一张 = 合成结果。

方向不需要任何假设，而且结论比「切换前后有变化」更强 ——
它证明的是**隐身开启时窗口对捕获画面的贡献完全为零**。

配套的排查小工具：

| 脚本 | 用途 |
|---|---|
| `scripts/verify-stealth.py` | 切换隐身前后抓屏对比（带隐藏窗口锚点），验证隐身是否真的影响系统捕获 |
| `scripts/alpha-probe.py` | **在受控纯色背景上**量窗口的真实不透明度。铺一块洋红满屏底再起应用，反解窗口级不透明度 β。背景已知 → 不受「背后是不是另一个透明窗口」干扰，这是唯一能给出可信 α 的做法 |
| `scripts/solid-bg.py` | 铺一块指定 RGB 的满屏纯色窗口，给 `alpha-probe.py` 当背景，也可单独用来做对照 |
| `scripts/measure-alpha.py` | 从 `verify-stealth.py` 的两张图**反解窗口的实际不透明度**，核对配置里的值有没有真的生效 |
| `scripts/alpha-diagnose.py` | 反解结果对不上时用它：把「背景近白」的像素按颜色簇拆开、用中位数/众数/仅深色样本三种估计分别反解，判断偏差是样本混入了浅色像素，还是透明度真有问题 |
| `scripts/shot.py` | 截取提词器窗口区域（`--full` 截整屏），排查渲染问题 |
| `scripts/list_windows.py` | 列出所有可见顶层窗口（标题 / 类名 / 尺寸 / 进程名），排查「进程在跑但找不到窗口」 |
| `scripts/win-rect.py` | 打印主窗口的**物理矩形 / DPI / 换算后的 CSS 尺寸**，以及配置里存的值。想知道"真实窗口到底多宽"问它，**别去看配置文件** —— 用户拖动过就不会同步成你以为的值 |
| `scripts/verify-click-through.py` | **真机**验证鼠标穿透：把光标依次停到窗口各处，读主窗口**自己的** `WS_EX_TRANSPARENT` 与 `WindowFromPoint` 的归属，判断此刻是可点还是穿透。带前端启动自检（见下文"白页"那条），没启动就直接报错而不是量一个假结果 |
| `scripts/crop-zoom.py` | 裁一块截图再放大 —— 46px 高的栏里的图标渲染，不放大根本看不清 |
| `scripts/diagnose-frontend-boot.py` | 启动 exe 并回答**「前端到底跑没跑」**：打印进程树 + `msedgewebview2.exe` 子进程数 + 日志里有没有 `[bootstrap]`。用来把"宿主环境不允许拉 webview"和"打包产物加载不了"这两件处置方式相反的事分开 |
| `scripts/open-app.py` | **打开应用** —— 老大说"帮我打开软件"时用它。启动当前 release 产物，并确认界面**真的**跑起来（要求 `[bootstrap]` 与 `可交互区已上报` **两条**日志都到）。已经在跑就只把它唤到前台、不重复启动（应用没有单实例守卫）；`--restart` 才换成新产物，且走**优雅关闭**（WM_CLOSE）而不是 `taskkill /F`。★ 进程用 **WMI** 拉起：从助手的 shell 里直接 `Popen`，哪怕带 `DETACHED_PROCESS`，命令一结束应用就被宿主的 job object 回收 —— 日志停在启动成功那一刻、一句退出记录都没有。`CREATE_BREAKAWAY_FROM_JOB` 试过，被宿主拒绝（`WinError 5`）；WMI 服务不在那个 job 里，才是真正独立 |
| `scripts/probe-webview-udd.py` | 探针：验证测试实例能不能用**独立的 user-data-dir**（`WEBVIEW2_USER_DATA_FOLDER`）从而不碰真 profile。**结论是不能** —— 环境变量被 Tauri 显式设的 data dir 覆盖，页面照样不执行。留着是为了别再走一遍这条死路 |
| `scripts/trace-frontend-boot.py` | A/B 对照：把 `click_through` 分别置为假/真各拉起一次，靠后端 `frontend_beat` 打点列出前端启动链路上**缺了哪一环**。release 没有 devtools 时，这是唯一能看出"跑到一半停了"的办法 |
| `scripts/test-heal-config.py` | 自测 `heal_leftover_config()`：造出"脚本被打断后该有的现场"（配置脏 + 副本在），验证下次运行确实能自愈。跑完会把真实现场原样放回 |
| `scripts/mic-crosscheck.py` | **用一套跟本项目无关的录音实现**（PortAudio 的 WASAPI / DirectSound / MME 三个后端）各录一遍，用"是否换一套实现就正常"来回答「没声音是我们的锅还是系统的锅」 |
| `scripts/audio-endpoint-probe.py` | 读出每个采集端点的**状态 / 静音 / 音量 / 声道数**，排查系统层的静音 |
| `scripts/check-state-shots.py` | 校验状态截图**真的拍到了那个状态**：① 各张两两不同（直接对应"裁错位置、拍到同一块地方"）；② 相对 `s-off` 基线的**强调色差值**在预期范围内（该亮绿/琥珀/蓝的亮了，不该亮的没亮）。★ 判据用"差值"而不是绝对值：基线里本来就有绿（大圆按钮的绿描边）和蓝（进度填充），绝对值等于永不失败。★★ **注意：它和 `shots/` 里那批图都是「改版前」那一版界面的**（期望的 class 还是 `mini-pill.demo.*`，`s-sp-*.png` 也还没重拍）⇒ 在本轮改版之后跑它**只会验到旧图**，拿到 ✅ 也不代表当前界面没问题 |
| `scripts/make-state-sheet.py` | 把状态截图拼成一张 `shots/states-sheet.png`，按「投屏隐身 / 演示模式 / 鼠标穿透」分组。**分开看每一张都是对的，只有摆在一起才看得出"两个状态用了同一个颜色"**。★ 同 `check-state-shots.py`：图是**改版前**的，本轮改版后要连图和断言一起重拍 |

> 最后两个是排查「麦克风没声音」用的。它们的价值在于**换一条独立路径去问同一个问题** ——
> 只在自己写的代码里打转，永远分不清是代码错还是设备坏。

实测输出（Windows 11 build 26200，洋红纯色底）：

```
与锚点(纯背景)的平均差：X = 142.8 灰阶（显著变化像素 92.90%），Y = 0.0 灰阶（0.00%）
判定：Y 是隐身生效时的捕获画面，X 是能看到界面的合成画面

✅ 隐身生效：捕获画面与「窗口隐藏」几乎完全一致（差 0.0 灰阶）
   —— 窗口对捕获结果的贡献为零，而不只是「有变化」。
✅ 对照组有效：不隐身时明显拍到了界面（与纯背景差 142.8 灰阶）
ℹ️ 反解出的不透明度 α ≈ 0.942（配置 0.94，来自 ...\cn.bobby.prompter\config.json）
[结论] 通过。
```

那次反解出来的 α = 0.942 与配置的 0.94 对得上，说明**透明度只生效了一次**，
没有被窗口级和 CSS 级重复相乘。

如果想单独、干净地量不透明度，用受控背景版本：

```bat
python scripts\alpha-probe.py
```

它会把桌面铺成洋红再启动应用，连拍三张（+0.8s / +2.5s / +5.5s）。
**连拍三张是必要的** —— 切换隐身之后 DWM 重新合成需要时间，太早截会拍到一张
「半透明鬼影」，从而误判成「窗口真的被降了透明度」。若第一张淡、后两张实，
那就只是过渡假象；三张都一样淡，才是窗口真的被多乘了一层透明度。

## 排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志里 `HotKey already registered`，热键只有一部分生效 | 已经有一个 Prompter 实例在跑，占着全局热键 | 任务管理器里结束旧的 `prompter.exe`（或旧的 `stealth-prompter.exe`）再启动 |
| 明明改了代码，重启后功能还是没出现 | **跑的是旧 exe** —— 改动只到源码/构建产物这一层，"已运行的那个进程"不会自己变 | 跑 `python scripts\diagnose-running-build.py`，它会直接告出"跑过的版本落后几版"。然后重新构建 + 重启 |
| 构建时报 `LNK1104: 无法打开文件 …\release\prompter.exe` —— 或 `failed to remove file … prompter.exe / 拒绝访问 (os error 5)` | **旧版 exe 还在跑**，文件被锁住，链接器写不进去（后一种是 Tauri 出包前想先把旧产物删掉，也删不动） | 先结束旧的 `prompter.exe` 再构建。**别试图靠改文件名绕过** —— `release\prompter.exe` 与 `release\deps\prompter.exe` 是同一个文件的硬链接（`nlink=2`），改掉一个名字文件本身照样锁着。★ 自己刚 `open-app.py` 打开过就要先关掉 |
| 窗口是纯黑/纯灰，看不到稿件 | 显卡驱动对透明窗口支持不佳 | 把 `tauri.conf.json` 里 `transparent` 改成 `false` 重新构建 |
| 窗口空白，显示「无法访问此页面 / ERR_CONNECTION_REFUSED」 | 跑的是开发模式产物，但 `vite` 没起来 | 用 `run-dev.bat` 启动（它会同时拉起 vite）；或用 `build.bat` 出一个不依赖 vite 的独立 exe |
| 自动化脚本报「前端没启动」，但窗口明明在、托盘也有、日志也在滚 | 脚本跑的是 **debug** 产物 —— 它去连 `localhost:5273` 的 vite（没起来）⇒ 前端是**白页**。窗口、后端、托盘全都正常，只有页面是空的 | 真机验证一律用 **release** 产物。`verify-click-through.py` 已经把这条做成硬门槛：日志里没出现 `[bootstrap]` 就直接报错退出，**不会去量一个假结果** |
| 同上，但用的**就是** release 产物，而且**同一个 exe 有时能起、有时不能起** | **WebView2 启动期的一次性失败**（不是我们的代码）：窗口与 `msedgewebview2.exe` 子进程都在，页面就是不执行。连续 `taskkill /F` 硬杀会提高这个概率 | 再跑一次即可。`verify-click-through.py` 现在会**自动重试 3 次**，最后一次把 profile 换成全新的（`EBWebView.bak-<时间戳>`）。**别把 flaky 当结论** —— 先重试 |
| 自动化脚本说「前端没就位」，但你看不出是卡在哪一步 | release 产物**没有 devtools**，前端"停在哪一步"从外面完全看不见。日志里有没有 `[bootstrap]` 只能区分"页面跑没跑"，分不出"跑到一半停了" | 用 `python scripts\trace-frontend-boot.py` —— 它靠后端的 `frontend_beat` 打点做 A/B，直接列出缺少了哪个环节。**注意："能测"要求 `[bootstrap]` 与 `可交互区已更新` 两条都在**：缺后者时后端按"整窗可交互"兜底，剖面会显示整窗可点，**和"穿透完全没实现"一模一样** |
| 跑完验证脚本，发现设置里的「鼠标穿透」自己打开了 | 脚本靠改 `config.json` 让实例带着穿透启动；**被打断时 `finally` 不保证执行**（Windows 上 `SIGTERM` = `TerminateProcess`，不可捕获），于是配置停在改动后的状态 | 不用手动改：脚本下次运行开头会自愈（改动前把原文件另存为 `config.json.verify-backup`）。自测见 `python scripts\test-heal-config.py` |
| 想把「验证实例」和老大正在用的实例隔离开，试过 `WEBVIEW2_USER_DATA_FOLDER` | **wry/Tauri 显式设了 data dir，这个环境变量不起作用**：临时目录确实被创建了（里面也有 `EBWebView`），但页面照样不执行。实测确认，别再走这条路 | 隔离只能靠"改 `%APPDATA%` 的配置 + 用完还原"（`verify-click-through.py` 已经在这么做）。负结果记在 `scripts/probe-webview-udd.py` 里 |
| 看不到提词器窗口 | 被 `Ctrl+Alt+H` 藏起来了 | 再按一次 |
| 用脚本截图，窗口区域只有背后的桌面、看不到提词器 | **应用默认自己隐身**（`stealth_on_start` 默认 `true`），已被排除出捕获 —— 这是设计如此，不是故障 | 先按 `Ctrl+Alt+S` 关掉隐身再截；或把配置里 `stealth_on_start` 改成 `false` |
| 窗口几乎看不见、太透 | `config.json` 里的 `opacity` 被设置抽屉的滑杆调低了（默认 0.94，最低 0.3） | 设置抽屉里拖回来；验证脚本会从该文件读期望值，所以这个值改了脚本也跟得上 |
| 控制台出现黄色「麦克风异常」 | 设备在送数字静音（多半是键盘上的麦克风静音键，这类静音在系统设置里查不出来） | 点它打开设置 → **麦克风自检**，会告诉你具体原因。也可以先跑 `python scripts\mic-crosscheck.py`：它用一套跟本项目无关的录音实现再录一遍，能直接回答「是我们的锅还是系统的锅」 |
| 开始识别后没反应 | 麦克风权限被拒，或设备被别的程序独占 | Windows：设置 → 隐私和安全性 → 麦克风 → 允许桌面应用。独占问题看控制台有没有「收不到任何音频数据」的警告 |
| 提示"模型文件缺失" | 模型未下载 | `python scripts\fetch-model.py` |
| 光标跟不上 / 乱跳 | 稿件与口述差异太大 | 设置 → 语音识别 → 「试一句」粘贴稿件原文验证算法本身是否正常；也可调低「跟读灵敏度」 |
| 拖文件进窗口没反应 | 不是受支持的格式，或拖的是多个文件、或文件编码无法识别 | 窗口顶部会出提示说明具体原因；若**完全没有任何提示**，说明拖放事件没到（见"排查"上方说明，需真机确认） |
| 拖 `.docx` 报"找不到正文" | Word 加密文档，或那是 `.doc` 改了个扩展名 | 用 Word 打开并「另存为 → .docx」 |
| 拖 `.docx` 报"不是有效的 Office 文件" | 它压根不是 ZIP（改名过的旧格式 / 文件损坏） | 同上 |
| 拖 `.pptx` 报"备注里没有文字" | PowerPoint 的备注页是空的 | 在 PPT 里「视图 → 备注」补上，或改用 `.docx` / `.txt` |
| 拖 `.pptx` 出的是幻灯片标题而不是讲稿 | 这份 PPT 完全没有备注页，于是退到了幻灯片正文 | 属预期行为（有备注时一定优先取备注）；补上备注即可 |
| 拖进来的是表格/文本框里的字，顺序有点怪 | 表格文字会按文档顺序抽出来 | 属预期行为 —— 提词器只保证"念到的字都在" |
| 改了稿子之后原文件变了 | **不该发生** | 编辑保存走的是"另存副本"，从不写回原文件。若真出现，说明用了「打开文件」之外的路径改了它，请记录现场 |
| `Ctrl+F` 弹出的是浏览器查找框 | 键被 WebView 自己抢了 | 属已知风险（未真机验证）；先用顶栏的放大镜按钮 |
| 粘贴浮层里点「读剪贴板」没反应 | WebView 不允许程序读剪贴板 | 按提示直接 `Ctrl+V` 粘到框里 —— 这条路一定可用 |
| 搜索时画面老是自己滚走 | 语音在推光标 | 查找打开期间自动滚动是关掉的；若仍在滚，说明查找栏已关闭 |
| 鼠标点不动窗口任何东西 | 穿透开着 | 按 `Ctrl+Alt+P` 关掉；热键也被占的话，**从托盘右键**菜单关 |
| 鼠标在稿件区点不到桌面上的东西 | 穿透没开（或光标还在控制区外扩 24px 的"接近环"里） | 按 `Ctrl+Alt+P` 开；若已开着，说明光标还没离控制区够远 |
| 窗口只剩一条细条 | 折叠态 | `Ctrl+Alt+M` 展开，或点细条右侧的展开按钮 |
| 任务栏 / 托盘里找不到图标 | 托盘创建失败（Linux 需要 appindicator，macOS 行为未验证） | 日志里搜 `[tray]`；不会影响主窗口，`Ctrl+Alt+H` 仍可显示 |
| 重启后窗口大小/位置不对 | 配置里存了越界值，已按设计回落默认 | 属预期行为；正常调好尺寸后关一次再启动即可记住 |
| 热键没反应 | 被其他软件占用 | 改配置文件里的热键，重启应用 |
| `npm` 报错崩溃 | `NODE_OPTIONS` 注入了垫片 | 用 `run-dev.bat`（里面已经清掉） |
