## 配图放哪（两个目录，不要混）

| 目录 | 用途 | 进不进仓库 |
|---|---|---|
| `img/` | **README 的配图**（ASCII 文件名，GitHub URL 干净） | ✅ 必须进 —— 不然线上是碎图 |
| `shots/` | 文档正文引用的截图（中文名、带编号） | ✅ 进，但注意**有旧图**：`s-sp-*.png` / `s-demo-*.png` 是改版前那一版界面的，`check-state-shots.py` 现在跑只会验到旧图 |

★ 仓库根目录那个 `shots/`（跟 `README.md` 同级）是**被 `.gitignore` 排掉**的调试截图堆 ——
要把里面的图用到文档里，**必须先复制进 `docs/img/` 或 `docs/shots/`**。

## ★★ 判据：一份文档该不该上产品页（README）

只问一句：**它的读者是「想用这个产品的人」，还是「我们自己」？**

| | 该上产品页 | 不该上 |
|---|---|---|
| 回答的问题 | 这是什么 / 怎么用 / 信不信得过 | 我们怎么干活的 |
| 例子 | 装法、快捷键、能力与边界、它凭什么做到 | 判据、需求拆解、竞品调研、缺口分析、上机清单、分发与推送操作 |
| 上不去怎么办 | — | 收进**本文档**，别在 README 里列 |

**为什么要把这条写下来**：README 的第一版（2026-10-09）就是栽在这 —— 我把「导航」
做成了「把 `docs/` 里的文件都列出来」，于是**竞品调研、上传 GitHub 操作指引**
这种东西也挂在了产品首页上。错的不是链接太多，是**列全清单不需要判断**，
而判断「谁会读这一页」需要 —— 一偷懒就会退回成目录。

★ 产品页的链接不是"目录"，是"读者读完这一页之后**真挚会有的下一个问题**"。
现在 README 里只留三个这样的链接（凭什么做到 / 我信吗 / 我自己验），其余一个都不留。

### 可检查的形态（别凭印象宣布"清干净了"）

```bash
grep -n '](docs/' README.md                                          # 每个链接落在哪一段
grep -n '分发\|上机\|竞品\|缺口\|判据\|拆解\|上传GitHub\|推送' README.md   # 关键词
```

**硬指标：产品段落（「改代码（开发者）」标题之前）里，`docs/*.md` 链接只应有 3 条**
（其余是 `docs/img/` 配图）；所有内部文档链接都必须落在**开发者段落**里。

★ 这条指标是**踩了两次**才写下来的：第一次是导航表列了 11 份；
第二次是我宣布"收到 3 条了"，却漏了正文里两处（`## 给另一台电脑用` 整节 +
「现状」末尾指向上机清单的链接）。
⇒ **导航表只是"内部文档出现的地方之一"** —— 清完必须机械搜一遍。

## ⚠️ 一个待定的问题：哪些文档不该公开

**这个仓库是公开的**（<https://github.com/renoo777/prompter>），
所以上面这些文档**现在对外可见**，包括：

* `产品分析-竞品调研.md` —— 我们的定位、定价思路、对竞品的威胁分级；
* `功能缺口分析.md` —— 对自己产品的失效模式分析（含"我们缺什么"的直话）。

**不把它们列在产品页 ≠ 它们不存在**，任何人点进 `docs/` 都能看到。
所以真正的决定是：**要不要让这些内容留在公开仓库里？**

三条路，各有代价：

1. **保持现状**（公开）—— 好处：一切透明，能自证"我们连自己的问题都写下来"；
   代价：竞品与潜在客户也能读到你对他们和对自己的判断。
2. **换个地方放**（私有仓库 / 本地）—— 好处：对外只留「怎么用」；
   代价：维护者文档失去版本历史与协作，且要从这个仓库里移走。
3. **留在仓库但不做二次编辑**（现状 + 不加产品页链接）—— 本次采用的做法；
   只解决了"首页观感"，没有解决"可见性"。

★ 这是产品决策，不是技术决策 —— **没有默认答案，需要拍板**。
在拍板之前，本文档不再对外宣传这些内容（但从 README 移除链接不是防护）。
